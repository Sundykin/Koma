# Koma 当前系统能力需求规格说明书

**版本**：v1.0  
**日期**：2026-05-20  
**范围**：仅描述当前代码已经实现并暴露的能力

## 1. 目的

本文把 Koma 现有实现转换为需求式逻辑描述，作为后续自底向上的重构基线。  
本文不描述未来愿景，只记录当前系统已经具备的能力、边界与限制。

## 2. 术语

| 术语 | 含义 |
|---|---|
| 业务根 | `~/.koma`，Koma 的业务数据根目录 |
| userData | Electron / Chromium 框架自管目录，当前被迁到 `~/.koma/_userData` |
| settings.db | 全局 SQLite，跨项目共享 |
| db/koma.db | 当前 storageRoot 下的结构化项目库 |
| workspace | 灵绘画布工作区 |
| task | 后台任务记录 |
| plugin | 可安装扩展包 |

## 3. 总体架构

Koma 当前是一个 Electron 桌面应用。主进程负责系统初始化、SQLite 存储、文件协议、后台任务、插件运行时和 marketplace；渲染进程通过 preload 白名单访问这些能力。

### 3.1 启动基线

- 业务根与 Electron 框架状态分离。
- 开发态可启用 Chromium remote debugging port，默认 `9333`。
- `koma-local://` 作为本地资源协议，供 renderer 安全读取业务根与 storageRoot 内资源。
- preload 负责注册 IPC 白名单，并在启动时初始化 services、任务恢复、更新器与插件市场。

**实现依据**：`electron/main.ts`、`electron/preload/index.ts`、`electron/preload/bridge.ts`、`electron/service/protocol.ts`、`electron/service/security.ts`

## 4. 功能需求

### FR-1 底层规划与运行基线

系统应提供稳定的 Electron 运行基线，确保业务数据不混入 Chromium 内部状态。

- 系统应把 `userData` 固定到 `~/.koma/_userData`，业务根固定为 `~/.koma`。
- 系统应注册 `koma-local://` privileged 协议，允许本地图片、视频、音频和 range 访问。
- 系统应通过 CSP 和 preload 白名单限制 renderer 能力边界。
- 系统应在启动时按固定顺序初始化本地协议、服务层、任务恢复、更新与插件市场。

**现状**

- 开发环境自动打印 remote debugging port。
- renderer 只能通过白名单 IPC 调主进程能力。
- 本地协议支持 `Range`、`Access-Control-Allow-Origin:*` 和常见媒体 MIME。

**实现依据**：`electron/main.ts`、`electron/preload/index.ts`、`electron/preload/bridge.ts`、`electron/service/protocol.ts`、`electron/service/security.ts`

### FR-2 持久化存储

系统应把结构化数据分层落库，并保持事务与迁移能力。

- 项目级结构化数据应落在当前 storageRoot 下的 `db/koma.db`。
- 全局配置、聊天历史、渠道配置、任务记录应落在固定的 `~/.koma/settings.db`。
- SQLite 应启用 WAL、外键和 schema migration。
- 项目导出 / 导入应支持整包迁移，保留结构化数据和资源文件。
- 灵绘工作区应支持导出 / 导入，并能重映射节点 / 分组 / 边 ID。

**当前数据域**

- 项目域：projects、characters、scenes、props、shots、shot_versions、assets、episodes、timelines、轨道、片段、转场、关键帧、动画。
- 灵绘域：workspaces、nodes、edges、groups、node runs、execution logs、workflow templates、workspace assets、history records。
- 系统域：channel_configs、media_defaults、app_settings_kv、chat_sessions、chat_messages、tasks。

**实现依据**：`electron/service/storage/schema.ts`、`electron/service/storage/BaseDB.ts`、`electron/service/storage/SettingsDB.ts`、`electron/service/project.ts`、`electron/service/linghui/index.ts`

### FR-3 文件存储与本地资源

系统应把文件操作和结构化持久化区分开，并对路径和来源做安全约束。

- 系统应允许 renderer 访问的文件根目录仅限 home、appData、userData、temp、业务根、当前 storageRoot 及少量资源目录。
- 系统应提供文件读取、写入、目录操作、复制、删除和下载能力，但必须先做路径校验。
- 系统应对远程下载做 SSRF 防护，并限制重定向次数。
- 系统应把 `koma-local://` 作为本地资源读取入口，支持图片 / 视频 / 音频直读。

**现状**

- 插件、项目、灵绘都把本地素材视为可落盘资源。
- 下载逻辑支持 Electron fetch / net.fetch 失败回退 Node http(s)。

**实现依据**：`electron/controller/fs.ts`、`electron/service/protocol.ts`、`electron/preload/bridge.ts`、`frontend/src/services/fileSystemPort.ts`

### FR-4 后台任务

系统应提供统一后台任务系统，支持主进程持久化、恢复、取消和广播。

- 任务记录应统一存入 `settings.db` 的 `tasks` 表。
- 任务应支持 `pending / running / completed / failed / cancelled` 等状态。
- 系统应支持按 scope、target、type 查询和清理任务。
- 系统应支持保留策略，包括按时间和按 scope 上限清理终态任务。
- 系统应支持启动恢复：可恢复任务在 boot 后重新入队。
- 系统应支持 main → renderer 的 delegate 调用，让主进程 handler 可以复用 renderer 侧业务代码。

**当前 handler 类型**

- `llm:complete`
- `shot-analysis`
- `script-analysis`
- `tti`
- `itv`
- `tts`

**现状**

- `TaskService` 负责存储、广播和 GC。
- `TaskRunner` 负责队列、并发控制、恢复和取消传播。
- renderer 侧仍保留兼容的任务状态与恢复逻辑。

**实现依据**：`electron/service/tasks/TaskService.ts`、`electron/service/tasks/TaskRunner.ts`、`electron/service/tasks/ipc.ts`、`electron/service/tasks/delegate.ts`、`electron/service/tasks/handlers/*`、`frontend/src/services/tasksIPC.ts`、`frontend/src/services/taskRunner.ts`

### FR-5 插件系统

系统应支持可安装、可验证、可激活、可停用的插件，并把插件能力纳入统一能力目录。

- 插件分类应支持 `provider / global / tool / mcp / agent`。
- 插件清单应包含 `id / name / version / category / engine / scopes / entry`。
- 插件安装前应做 manifest shape 校验、兼容性校验和签名校验。
- marketplace 安装应支持下载、SHA512 校验、解压、备份回滚和热加载。
- 插件运行时应支持后端模块加载、激活 / 停用 / 卸载。
- 插件应可以注册 Provider、MCP server / tool / resource、Worker Agent，以及统一 Capability。
- 插件应只能在授权 scope 内访问 settings、projects、prompts、storage、network、MCP、agent 和 spawn。
- 前端插件应支持 UI 组件、菜单项和弹窗等受控宿主交互。

**当前能力**

- Provider 插件可映射为渠道配置，并受 `media-request-v1` 契约约束。
- MCP 工具名会被强制命名空间化为 `pluginId:toolName`。
- CapabilityRegistry 可按 id / tag 解析能力并统一调用。
- `PluginAPI` 目前提供 `settings / projects / prompts / channels / storage / ui / activation`。
- `PluginManager` 支持查看、启用、停用、卸载和打开插件目录。

**实现依据**：`electron/service/plugin/types.ts`、`electron/service/plugin/compatibility.ts`、`electron/service/plugin/runtime.ts`、`electron/service/plugin/bridge.ts`、`electron/service/plugin/index.ts`、`electron/service/plugin/registries/*`、`electron/service/plugin/capability/*`、`electron/service/marketplace/*`、`electron/controller/plugin.ts`、`frontend/src/services/plugin/*`、`frontend/src/store/pluginStore.ts`、`frontend/src/components/plugins/*`

### FR-6 系统数据管理

系统应把全局设置、最近项目、聊天历史、prompt 模板和渠道配置分层管理。

- 渠道类配置应存 `settings.db`，非渠道设置应存 `settings.json`。
- 最近项目应作为全局 KV 持久化，并保留最近 20 条。
- 聊天会话应只保存有消息的会话，消息明细落 SQLite。
- Prompt 模板应支持全局约束、系统提示、剧本 / 分镜 / 提取 / 推文 / TTI / ITV 等分组。
- 项目域应支持自动保存、防抖保存与退出前保存。
- 存储根路径应可配置、可迁移，并默认指向 home 下的 `.koma`。

**现状**

- `settings.core` 会把 `settings.json` 与 `settings.db` 合并后提供统一 `AppSettings`。
- `channelConfig` 是 SQLite-only，浏览器环境不再提供 localStorage 回退。
- `autoSaveService` 以 projectId 为粒度管理 dirty/saving/saved/error。
- `taskRecoveryService` 会扫描未完成媒体任务并恢复执行。

**实现依据**：`frontend/src/store/settings/core.ts`、`frontend/src/store/settings/channelConfig.ts`、`frontend/src/store/settings/mediaConfig.ts`、`frontend/src/store/settings/recentProjects.ts`、`frontend/src/store/chatHistoryStore.ts`、`frontend/src/store/promptTemplates.ts`、`frontend/src/store/storageConfig.ts`、`frontend/src/store/autoSaveService.ts`、`frontend/src/store/taskRecoveryService.ts`、`frontend/src/store/projectStore.ts`

### FR-7 主题系统

系统应支持应用主题切换和项目风格预设两套不同层级的主题能力。

#### FR-7.1 应用主题

- 系统应提供 4 套应用主题：
  - `dark-emerald`
  - `dark-business`
  - `light-business`
  - `high-contrast`
- 系统应通过 ThemeProvider 把 token 编译为 CSS 变量并同步 AntD ConfigProvider。
- 系统应持久化当前 themeId，并在启动时恢复。

#### FR-7.2 项目风格预设

- 系统应提供项目风格预设：
  - `anime-urban`
  - `anime-xuanhuan`
  - `anime-classical`
  - `anime-pixel`
  - `custom`
- 项目风格预设应生成 `ProjectStyleSnapshot`，并影响 TTI 风格前缀与 LLM prompt 后缀。

**现状**

- 主题切换 UI 直接读取主题 swatch。
- 项目风格预设与应用主题是两个独立系统，不共享 ID 语义。

**实现依据**：`frontend/src/theme/themes/*`、`frontend/src/theme/runtime/ThemeProvider.tsx`、`frontend/src/theme/compile/themeToCssVars.ts`、`frontend/src/components/settings/AppearanceThemeSettings.tsx`、`frontend/src/config/themePresets.ts`

## 5. 现状限制

- `ProjectService` 当前使用共享的 `db/koma.db` 作为结构化项目库，不是每个项目一个独立数据库文件。
- `linghui_global_assets` 的建表逻辑只在迁移段落中出现，初始建库路径需要复核。
- `tool` 类插件当前更偏前端宿主能力，后端 runtime 不把它当成独立后端能力注册。
- 旧的 renderer 侧任务 / 插件兼容层仍保留，用于平滑过渡和 UI 兼容。

## 6. 结论

Koma 当前已经具备完整的桌面应用底座：SQLite 分层持久化、受限文件访问、可恢复后台任务、可安装插件、分层系统数据管理，以及应用主题和项目风格两套主题系统。  
后续重构应以本文的现状边界为准，不应把未实现能力写回成“已存在”。

**源码入口总览**：`electron/*`、`frontend/src/store/*`、`frontend/src/services/*`、`frontend/src/theme/*`、`packages/plugin-sdk/*`
