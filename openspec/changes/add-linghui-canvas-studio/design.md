## Context

“灵绘”不是现有分镜页的一个模式切换，而是一个面向分镜师、短视频创作者和 IP 创作者的独立工作台。它需要：

- 直接从侧边栏进入，而不是先选择短剧项目或剧集
- 用节点画布表达创作流程，而不是表格式 Shot 列表
- 承载批量生成、分组运行、多角度对比、宫格输出和分镜序列预览

当前仓库中已经存在两个容易混淆的能力：

- 现有 `editor/storyboard`：服务于短剧项目内的分镜生产
- 现有 `add-grid-storyboard-mode` 提案：服务于分镜页内的九宫格生成

它们都不满足“独立菜单 + 独立工作区”的产品要求。

## Goals / Non-Goals

- Goals:
  - 为 Koma 增加一个名为“灵绘”的一级工作台入口
  - 让“灵绘”拥有独立工作区模型、独立保存与导出能力
  - 在 MVP 中落地节点化画布、分组、4 宫格、多角度、分镜组与批量结果管理
  - 使用前端工作流调度来执行节点依赖、局部重跑和批量分发
- Non-Goals:
  - 不替换现有 `ProjectOverview`、`EditorView`、`Storyboard` 流程
  - 不要求首版支持完整运镜视频生成
  - 不要求首版支持 9 宫格、自定义角度、视频拼接、音频混流
  - 不将“灵绘”首版包装为插件或外挂模块
  - 不与现有 `Project / Episode` 模型做强耦合迁移

## Decisions

### Decision: “灵绘”首版作为内建一级页面，而不是全局插件

`Sidebar.tsx` 和 `App.tsx` 已经证明应用支持多个一级工作台视图。虽然全局插件也能挂到侧边栏，但 `PluginHost` 和 `PluginAPI` 更适合承载边界清晰的独立工具，不适合首版就承担复杂画布、任务队列、媒体服务与工作区存储。

**Why**

- 需要深度接入导航、懒加载页面、任务状态、媒体生成服务和本地存储
- 首版要做高频交互与复杂状态，插件 API 目前不够厚
- 作为官方核心能力，首版内建更容易保证体验一致性

**Alternatives considered**

- 使用 global plugin 形态承载“灵绘”：可行，但会把核心产品能力压在插件生命周期和权限模型上，增加维护复杂度

### Decision: “灵绘”使用独立 `LinghuiWorkspace` 存储域

现有 `storage` 规范围绕短剧项目组织 `project.json`、`meta.json`、`episodes` 和分镜版本。把“灵绘”硬塞进相同模型会迫使节点画布去适配剧集/分镜语义，不利于独立菜单定位。

**Why**

- “灵绘”可以在没有短剧项目的情况下直接创建和运行
- 画布工作区的核心对象是 `workspace / node / edge / group / run`，不是 `project / episode / shot`
- 独立存储更利于后续支持单独导入导出与模板复用

**Alternatives considered**

- 复用 `projects/{projectId}`：会污染现有项目索引、状态字段和创建流程

### Decision: MVP 节点集合严格收敛到用户给出的核心范围

MVP 覆盖：

- 参考图节点
- 提示词节点
- 图生图节点
- 图生视频节点
- 4 宫格生成节点
- 多角度生成节点（仅预设角度）
- 分镜节点
- 分镜组节点

不进入 MVP 的节点和能力：

- 运镜节点
- 9 宫格生成
- 自定义角度
- 视频拼接
- 视频加音频
- 风格控制节点 / 参数配置节点 / 批量生成节点的完整版本

**Why**

- 这些能力与用户文档中的 MVP 列表一致
- 可以先把“独立菜单 + 画布心智”跑通，再补更复杂的视频后处理

### Decision: 前端负责编排图执行，后端继续提供单步生成接口

“灵绘”的执行模型采用前端拓扑排序与状态管理，后端继续暴露单步生成能力。批量节点（4 宫格、多角度、分镜组）由前端拆分任务并并发调度。

**Why**

- 与用户文档中的“前端调度工作流”一致
- 便于在画布上实时标记依赖、高亮受影响节点和支持局部重跑
- 可以复用现有媒体 Provider 和任务状态体系

### Decision: 页面布局采用固定四区壳层

“灵绘”工作台在视觉上固定为：

- 顶部工具栏：新建、打开、保存、运行、导出、视图控制
- 左侧节点库：分类、搜索、拖拽添加
- 中部画布：节点、连线、分组、视口
- 右侧面板：属性、进度、结果预览
- 底部状态栏：任务队列、日志、快捷键帮助

**Why**

- 与用户文档的交互模型一致
- 适合容纳大量操作而不挤占画布空间
- 便于后续扩展分镜播放器与模板中心

### Decision: 批量结果以“组合结果 + 明细结果”双层模型保存

4 宫格、多角度和分镜组都不是单文件输出，应统一保存：

- 组合结果：宫格大图、分镜序列、对比视图清单
- 明细结果：拆分单图、按角度命名的图片、逐分镜帧

**Why**

- 方便右侧预览面板与批量下载
- 便于后续做“替换单图”“重跑单个角度”这类细粒度操作

## Risks / Trade-offs

- 独立工作区会形成第二套创作入口
  - Mitigation: 明确“灵绘”面向画布创作，不替代现有短剧生产线
- 节点图执行与多模型能力可能出现不一致
  - Mitigation: MVP 先只覆盖已有稳定的 TTI / ITV 能力，复杂视频节点延后
- 批量节点会提高任务和存储压力
  - Mitigation: 定义独立输出目录与运行记录，并支持单节点/单角度重跑
- 后续如果需要与项目资产互通，独立存储会带来桥接成本
  - Mitigation: 首版先做导入式复用，后续再补跨工作区资源桥

## Migration Plan

这是一个纯新增能力，无需迁移现有项目数据。

首版上线只需要：

1. 增加 `灵绘` 一级导航入口
2. 增加独立 `linghui-workspaces` 存储域
3. 保持现有项目、分镜、导出流程行为不变

## Open Questions

- 首版是否允许从现有短剧项目资产面板直接导入角色/场景图到“灵绘”素材库，还是仅支持本地上传？
- “灵绘”工作区导出包是否使用独立扩展名（如 `.linghui.zip`），还是继续沿用 `.koma.zip` 体系？
- 多角度生成首版是否允许单角度局部重跑，还是只支持整组重跑？
