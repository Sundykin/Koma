## Context

当前执行引擎已经使用拓扑排序来组织节点顺序，但当图里出现环时，排序函数会把剩余节点直接追加到尾部。这会让真正的问题从“图非法”退化成“执行表现古怪”，排查成本高。

同时，`rfTypeToLinghuiType()` 用 `replace(/-/g, '/')` 做转换，只要传入一个结构类似的字符串，就有机会被错误地当成合法类型。

## Goals / Non-Goals

**Goals**

- 在工作流执行入口对环依赖给出明确失败
- 让 RF 类型与灵绘类型之间的转换只接受显式已知映射
- 用测试覆盖这两类失败路径

**Non-Goals**

- 不在本轮改造 prompt reference 面板的引用遍历策略
- 不引入更复杂的图诊断 UI

## Decisions

### Decision: 拓扑排序发现环时直接抛错

`topologicalSort()` 将不再静默追加未排序节点，而是：

- 收集当前 required 子图里的未排序节点
- 抛出明确错误，提示存在循环依赖

Why:

- 执行层比静默容错更适合“早失败”
- 这样可以避免后续节点拿到不完整上游状态

### Decision: 类型转换使用显式映射表

`LinghuiNodeType` 与 `LinghuiRFNodeTypeKey` 之间将维护一张双向映射表，而不是依赖字符串替换。

Why:

- 节点类型集合很小，显式映射成本低
- 可以防止未来新增带短横线的类型时被错误替换

## Risks / Trade-offs

- 旧数据如果通过导入或外部篡改形成了环，之前可能“勉强执行”，现在会直接失败；但这是更正确的行为
- `rfTypeToLinghuiType()` 对未知类型将回退为默认已知类型或抛错策略更严格，依赖非法类型输入的调用方会更早暴露问题

## Migration Plan

1. 先补 OpenSpec 和测试
2. 再收紧拓扑排序和类型映射实现
3. 用目标测试验证正常路径不受影响、异常路径可诊断
