## Context

项目工作流已经把剧本拆解为 `Shot`，并通过统一的视频能力路由生成每个分镜的视频。当前每个分镜只从自己的分镜图、角色、场景和道具参考开始，无法在镜头切换处复用上一镜真实视频的结束状态。项目数据通过 SQLite 的 `shots.metadata_json` 保存部分可选字段，媒体则以 `StoredMediaAsset` 记录本地路径、远程地址和生成版本。

本变更横跨剧本拆解、项目持久化、参考图编译、FFmpeg 媒体处理、单镜/批量视频工作流和项目分镜卡片。必须保持旧项目可加载，并且不能把实现扩展到 Linghui 模块。

## Goals / Non-Goals

**Goals:**

- 为项目 `Shot` 保存可解释、可恢复的相邻镜头连续性决策。
- 在有连续性需求时，把上一分镜当前真实视频的尾帧作为本镜最高优先级视频参考图。
- 支持用户手动继承、手动独立、立即截取、重新截取和恢复自动判断。
- 让批量生成按连续性依赖调度：有依赖的镜头等待前镜成功，其余镜头继续并行。
- 对旧数据提供确定性规则兜底，并对尾帧抽取失败给出可诊断错误。

**Non-Goals:**

- 不改动 Linghui 的脚本节点、编辑器或执行器数据模型。
- 不新增独立的视频剪辑/转场编辑器，也不改变视频供应商能力协议。
- 不把封面首帧、分镜图片或故事板图片冒充为上一视频尾帧。
- 不自动删除旧视频版本；尾帧只绑定到生成时使用的当前视频版本。

## Decisions

### 1. 将连续性元数据放在项目 Shot 的可选字段中

在 `Shot` 顶层增加 `videoReference`，包含 `mode`（`auto`/`manual`）、`usePreviousTailFrame`、原始自动建议、理由、来源 Shot、已截取的 `StoredMediaAsset`、截取时间和来源视频版本键。通过已有 `metadata_json` 序列化，未设置字段的旧 Shot 保持可读；解析时只接受受支持的枚举和值，异常内容丢弃并走兜底规则。

选择 metadata 而不是新增 SQLite 列，是因为该信息是可选的、需要随 Shot 原子保存，且当前迁移系统已经允许扩展 metadata。手动覆盖不覆盖 `autoUsePreviousTailFrame`，因此“恢复自动”不需要重新调用 LLM。

### 2. 在所有分镜合并、编号之后计算连续性

LLM 的分镜拆解输出增加可选的连续性建议字段；长剧本按 chunk 生成时，服务先合并并分配最终 Shot ID，再按最终顺序运行确定性规范化。规则优先识别明确转场、场景切换、时间跳跃、闪回/平行叙事并判定独立；同场景、角色交集、动作/视线/机位延续等信号才建议继承。第一镜永远独立。这样不会因 chunk 边界或旧数据缺字段而错误继承。

### 3. 尾帧抽取由 FFmpeg 服务统一负责并缓存

在现有 FFmpeg 管理器中增加 `getTailFrame`。输入先物化为 FFmpeg 可读的本地文件（本地路径、远程 URL、data/blob 均支持），读取时长后在结束前 50–120ms 取单帧，按媒体版本键缓存。抽帧失败、视频不存在或视频仍未完成时返回可区分错误；绝不回退到 `getPosterFrame`。

### 4. 尾帧在参考 bundle 中拥有最高优先级

增加 `previous-video-tail` 引用项并放在 bundle 的第一个位置，保留当前分镜图、用户参考、角色、场景和道具作为补充。编译 `video.reference-to-video` 时尾帧进入 `referenceImages[0]`；编译 `video.image-to-video` 时尾帧作为 `primaryImage`，原有分镜图等放入 additional references。提示词编译支持 `@previous_tail_frame`，将其映射为实际 `@Image N`，让供应商和日志都能识别连续性锚点。

### 5. 批量视频采用依赖感知调度

批量入口建立 shot ID 到任务的有向依赖图。没有尾帧依赖的任务按既有并发上限运行；依赖上一镜的任务只有在上一镜成功且当前视频可读取后才入队。上一镜不在本批次时使用已持久化的当前视频；没有真实视频或尾帧抽取失败则本镜失败并显示原因。生成完成后继续通过统一保存路径刷新 Shot/版本媒体状态。

### 6. UI 明示自动判断与人工覆盖

`ShotCard` 展示“自动继承/自动独立”及理由、当前生效模式、尾帧缩略图和来源镜头。用户可以启用/禁用上一镜尾帧、截取或重新截取、取消继承、恢复自动；只有上一镜存在真实视频时截取按钮可用。保存通过现有 `saveAllShots`，状态变更不触碰 Linghui 页面。

## Risks / Trade-offs

- [Risk] 旧项目的场景/动作字段不完整，规则判断可能偏保守 → 默认独立并展示“信息不足”的理由，允许用户手动继承。
- [Risk] 远程视频下载或 FFmpeg 抽帧耗时、失败 → 使用版本键缓存，提供阶段进度和明确错误；不阻塞无依赖镜头。
- [Risk] 某些模型限制参考图数量 → 尾帧先保留，按现有 capability/max-reference 规则裁剪低优先级补充项并记录裁剪日志。
- [Risk] 批量任务失败后下游依赖无法执行 → 将依赖失败传播为“缺少上一镜尾帧”的可重试失败，其他独立分支继续执行。
- [Risk] metadata schema 演进导致脏数据 → 解析严格校验并忽略未知字段，写回时只输出当前受支持字段。

## Migration Plan

1. 先发布类型、解析和规范化逻辑；旧 Shot 缺少 `videoReference` 时按规则生成内存默认值，不要求数据库迁移。
2. 发布尾帧抽取、参考 bundle 和依赖调度；旧项目首次生成视频时按当前视频版本建立尾帧绑定。
3. 发布项目分镜卡片交互；用户的手动选择随 `saveAllShots` 持久化。
4. 若回滚，实现可停止读取新字段并继续生成原有独立视频；metadata 中的未知字段会被安全忽略，已有视频媒体不受影响。

## Open Questions

- 当前版本不要求用户配置尾帧偏移；实现使用 50–120ms 的安全窗口，后续可按供应商补充配置。
- 是否为尾帧增加独立媒体表槽位留待后续媒体清理需求；本变更先复用 `StoredMediaAsset` 嵌入 Shot metadata。
