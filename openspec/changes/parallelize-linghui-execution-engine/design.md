## Context

当前 `executeLinghuiWorkflow` 使用单个 `for ... of orderedNodes` 循环串行执行所有必需节点。虽然已经基于拓扑排序保证了依赖正确性，但同层无依赖节点仍然只能逐个等待。

现有实现还把队列中的“运行中节点”建模为单个 `runningNodeId`。这对串行模型成立，但无法准确描述并发层中的多个运行中节点。

## Goals / Non-Goals

**Goals:**

- 在不改变 `ExecutionNodeView`、节点执行器和 Provider 调用契约的前提下，引入按拓扑层级的并行调度
- 让执行队列能表达多个运行中节点，并继续提供完成、失败、取消统计
- 保持错误隔离和取消语义，避免一个并发分支的普通失败中断整层执行
- 用测试锁定并发开始时机、依赖等待和队列状态

**Non-Goals:**

- 不在本轮引入用户可配置的并发上限或 Provider 级限流器
- 不改动节点执行器内部逻辑，也不修改现有执行结果契约
- 不重做页面层的执行状态 UI，只提供更准确的数据结构

## Decisions

### Decision: 先把拓扑排序升级为拓扑层计划

执行引擎先把待执行子图转换为若干层，每层内的节点都只依赖前面层的结果。执行阶段按层推进，每层内部使用 `Promise.all` 并发运行。

Why:

- 可以最大化复用现有依赖分析
- 同层节点天然互不依赖，适合作为第一版并发边界
- 比“边跑边动态出队”更容易验证取消和失败语义

### Decision: 队列状态增加 `runningNodeIds`，保留 `runningNodeId` 兼容字段

队列状态增加数组字段表示所有正在运行的节点，同时保留单值字段作为兼容别名，始终取第一个运行中节点。

Why:

- 并发层需要准确表达多个运行中节点
- 当前调用方没有依赖单值字段，但保留兼容别名能降低潜在外部调用风险

### Decision: 普通执行失败不取消同层其他节点

层内节点的普通错误会各自落为 `failed`，其余并发节点继续完成。下一层开始前，依赖失败上游的节点会被快速标记为“上游节点执行失败”。

Why:

- 这符合架构分析里“错误隔离”的预期
- 用户可以在一次运行中看到尽可能完整的成功/失败结果，而不是因为单点故障整层报废

## Risks / Trade-offs

- [同层并发可能放大 Provider 请求压力] → 本轮先限定为“按层并发”，不做跨层并发；后续再评估限流策略
- [队列回调次数增加] → 继续沿用轻量对象更新，优先保证状态正确，必要时后续再做节流
- [取消时存在部分节点已完成、部分节点已取消的混合状态] → 明确保留已完成结果，只把仍在运行或未启动的节点标记为取消

## Migration Plan

1. 新增拓扑层规划函数和并行队列状态字段
2. 将工作流执行循环替换为“逐层调度 + 层内并发”
3. 补充工作流测试并跑定向验证
