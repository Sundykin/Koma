## Context

架构分析文档把当前灵绘执行层的问题分成了两类：

- 节点能力与实际执行不一致，导致用户输入被静默忽略
- 同一份节点数据在不同执行路径中的含义不一致，导致下游节点看到的结果不稳定

这次 change 不处理更大的 Store 化、并行执行或 Electron 解耦，而是优先修复一批会直接影响当前节点工作流正确性的契约问题。

## Goals / Non-Goals

**Goals**

- 让多角度图片节点始终遵守“必须有上游参考图”的契约
- 让多角度请求保留用户明确填写的 prompt，而不是只留下角度描述词
- 让批量图片结果在下游引用时不再丢失 `items`
- 让脚本节点在生成态与静态解析态都保持一致的结构化输出契约
- 用测试覆盖本轮修复，避免旧行为回归

**Non-Goals**

- 不在本轮引入视频节点真正的音频到视频生成协议
- 不处理灵绘画布 Hook 复杂度、并行执行引擎或基础设施端口化
- 不重构 `LinghuiNodeResult` 为区分联合类型
- 不改动节点 UI 结构，除非执行契约修复直接要求

## Decisions

### Decision: 多角度图片不再静默降级

当图片节点显式开启 `multiAngle.enabled` 时，执行层必须把它视为严格的图生图路径：

- 没有上游参考图时直接报错
- 不因为用户填写了 prompt 就改走普通文生图

Why:

- 多角度是明确的工具意图，不应该在用户无感知的情况下换成另一种生成模式
- 失败比“看起来成功但结果类型错误”更容易理解和修复

### Decision: 多角度请求同时保留原始 prompt 与角度 prompt

多角度请求编译将保留两层语义：

- `originalPrompt`: 用户输入的主体、服装、风格等描述
- `anglePrompt`: 由多角度参数派生出的视角描述

`compiledPrompt` 需要同时包含两者，这样：

- 专用多角度接口可以同时看到 `originalPrompt` 和 `anglePrompt`
- 退回到通用图生图 provider 时，请求 `prompt` 仍然保留完整语义

### Decision: 共享参考图收集遵循“主图优先，全集透传”

`collectReferenceSources` 不再只看 `result.primary`，而是按如下顺序收集唯一图片源：

1. 当前结果的 `primary`
2. 当前结果里的其他 `items`

Why:

- 图片节点已经支持批量生成和主图选择，下游引用应拿到整组图片而不是第 1 张
- 先放主图可以保持现有“当前选中主图优先”语义

### Decision: 脚本节点统一走结构化解析契约

脚本节点的两条路径都要复用同一份解析规则：

- 生成态：默认 JSON 约束始终保留，用户自定义系统提示词追加到默认约束后
- 静态解析态：手动脚本通过 `parseLinghuiScriptContent` 输出 `formattedText`、`shots` 与首帧信息

Why:

- 这样可以让执行路径和静态解析路径看到一致的数据结构
- 自定义提示词仍可表达风格要求，但不会破坏解析器依赖的输出格式

## Risks / Trade-offs

- 某些用户如果之前依赖“多角度无图时自动退回文生图”的旧行为，会在本次变更后收到明确错误
- 多角度 `compiledPrompt` 变长后，个别 provider 的提示词表现可能略有变化
- 下游节点开始消费整组图片后，部分模型请求会比之前携带更多参考图，但这是更符合节点语义的行为

## Migration Plan

1. 先更新 OpenSpec 与测试，明确旧行为不再成立
2. 再修正多角度 prompt 编译和图片参考透传
3. 最后统一脚本节点的系统提示词与静态解析路径
4. 运行目标测试验证执行层行为

## Open Questions

- 本轮不处理“视频节点音频输入真正参与 ITV 请求”的能力扩展，后续可作为单独 change 推进
