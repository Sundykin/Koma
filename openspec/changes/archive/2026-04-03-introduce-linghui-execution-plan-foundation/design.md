## Context

灵绘已有一套成熟的执行编排链路：

- `LinghuiPage.tsx` 负责运行入口与运行状态管理
- `executeLinghuiWorkflow()` 会解析依赖、按拓扑层并发执行
- `executionQueue` 可以反映当前运行进度

但在真正开始执行前，系统没有任何“计划层”：

- 用户不知道本轮需要补跑多少前置节点
- 不清楚哪些节点会并行、哪些层会成为瓶颈
- 不知道根据历史执行情况大概要等多久
- 成本元数据不存在时，也没有显式告知“当前无法估算”

5.3.3 的第一块不需要直接做完整的历史统计中心或成本结算系统。更合适的 foundation slice，是先把“执行前 explain”落地成纯分析服务和确认弹窗，并只挂在批量执行入口。

## Goals / Non-Goals

**Goals:**

- 抽出可单测的执行计划构建服务
- 复用当前依赖图分析逻辑，生成波次、最大并行度与瓶颈节点
- 基于历史 run duration + 节点类型启发式生成预估总耗时
- 在运行全部 / 运行选中前展示执行计划确认弹窗
- 对成本不可估的情况给出显式说明

**Non-Goals:**

- 不在本轮改造单节点快速执行
- 不引入真正的 provider 定价表或计费系统
- 不更改实际执行队列的并发策略
- 不在本轮持久化完整执行计划历史

## Decisions

### Decision: 计划构建服务与执行编排共享同一套图分析基础

首版将依赖收集与拓扑分层逻辑抽到共享分析模块，由执行计划与真正执行流程共同复用。

Why:

- 避免“计划层”和“执行层”分析结果不一致
- 能直接复用现有循环依赖检测
- 执行计划服务可以保持纯函数、易测

### Decision: 批量执行前展示 Modal，单节点执行保持直达

首版仅在“运行全部”和“运行选中”前展示计划确认弹窗；单节点运行继续直达。

Why:

- 批量执行更需要 Explain，单节点链路则更强调即时性
- 改动面更小，不会打断已有节点内快速运行体验

### Decision: 预估耗时优先使用历史 run duration，缺失时退回节点类型启发式

对每个节点：

- 若上次运行存在 `startedAt` / `updatedAt` 且时长有效，则使用历史时长
- 否则按节点类型使用启发式默认值

整体预估总耗时为各并行波次中最长节点时长之和。

Why:

- 与当前数据结构直接兼容，不需要新表
- 能反映并行执行的真实等待上界
- 即使新节点没有历史，也能给出可用的粗估

### Decision: 成本字段允许显式不可估

执行计划首版包含成本摘要区域，但当当前上下文拿不到稳定 provider 价格元数据时，返回 `unavailable` 状态并在 UI 中直说“暂不可估”。

Why:

- 当前仓库没有稳定的灵绘 provider 定价源
- 伪造价格会比承认不可估更误导
- 为后续接入真实价格元数据保留了 UI 与数据位

## Risks / Trade-offs

- [历史时长可能受上次网络波动影响] → 与启发式一起展示，定位为估算而非 SLA
- [只拦截批量执行，不拦截单节点] → 首版体验更稳，但单节点仍没有 Explain；后续可再扩展
- [成本暂不可估] → 与架构终态相比不完整，但比给出错误价格更安全

## Migration Plan

1. 抽出共享图分析与执行计划构建服务
2. 接入执行计划确认弹窗到批量执行入口
3. 展示并行波次、预估时长、瓶颈节点和成本状态
4. 补充执行计划分析测试
