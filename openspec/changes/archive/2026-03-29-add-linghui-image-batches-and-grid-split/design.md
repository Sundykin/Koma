## Context

灵绘当前的图片节点只在属性层保存单个 `source`，执行层虽然能返回多张结果，但节点 UI、下游引用和提示词编译仍然按照“单图节点”思路工作。这导致：

- 导入模式无法把多张图片组织成一个节点
- 多张生成结果缺少节点内选图与主图切换
- 下游经常拿到整组图片而不是用户确认后的主图
- 现有 `gridType` 更像“生成数量”，无法承载“切分当前图并继续生成节点”的真实宫格工作流

本次改动跨越图片节点数据模型、节点 UI、下游引用、执行链路、画布插入能力和 Electron FFmpeg 服务，因此需要单独设计。

## Goals

- 让图片节点支持最多 4 张图片的统一集合体验
- 保持集合内图片比例一致，避免节点内部出现混乱的画面比例
- 让主图成为图片节点对外唯一暴露的图片输入
- 让节点本体能直接浏览图片，并在多图场景下快速展开查看
- 提供可视化的宫格切分工具，并把切分结果自动送回画布

## Non-Goals

- 不把图片节点扩展成完整资产库
- 不在本轮引入图片集合的自由排序或拖拽重排
- 不实现云端高清模型，只使用本地 IPC/FFmpeg 处理
- 不改视频节点或音频节点的数据模型

## Decisions

### 1. 图片节点使用“导入集合 + 运行集合 + 主图指针”的模型

图片节点属性层新增导入集合和主图标识，运行结果层保持现有 `primary + items` 结构，但所有消费方都通过统一 helper 解析“当前有效主图”，而不是直接读取 `result.primary`。

这样可以同时覆盖：
- 导入模式：主图来自属性层集合
- 生成模式：主图来自运行结果集合 + 属性层选中的 `primaryResultSource`
- 兼容旧数据：旧节点仍可从单个 `source` 迁移到一张图片的集合

### 2. 下游只消费主图，不再默认消费整组图片

图片节点一旦进入“多图集合”模式，连接到下游的语义必须保持单图确定性。执行链、提示词引用和上游展示都只暴露主图，避免出现：

- 下游自动拿到整组图片导致参考顺序混乱
- `@Image n` 编译结果和用户当前选中的主图不一致

多图集合仍会在图片节点内部显示，但它不自动扩大为多图输出语义。

### 3. 生成数量与宫格切分解耦

多张生成使用 `batchCount`，限制为 `1-4`。宫格切分改为独立工具，不再复用生成时的 `gridType` 作为输出数量配置。

这样可以避免把“让模型生成 4 张图”和“把当前图切成 4/9/16/25 块”混成一个概念。

### 4. 宫格切分基于当前主图进行

宫格工具始终作用于图片节点的当前主图。工具流程：

1. 解析当前主图尺寸与比例
2. 在工具面板中显示放大预览与网格叠加
3. 用户选择 4 / 9 / 16 / 25 宫格布局
4. 用户多选若干宫格
5. IPC 调用 FFmpeg 先做切图，再把选中格子放大到与原图同尺寸比例
6. 画布自动生成若干导入图片节点

### 5. FFmpeg 服务扩展为通用 NxN 切分

现有 `splitGridImage` 仅覆盖 3x3。此次扩展为支持 2x2 / 3x3 / 4x4 / 5x5，并输出所有格子文件。前端负责挑选选中的格子，再触发二次高清化输出。

### 6. 新生成的切图节点按“导入图片节点”插入原节点附近

切图产生的新图片不会回写到原节点集合中，而是在画布中创建新的图片节点。这样更符合“把当前图拆成若干子图继续编排”的工作流心智，也避免污染原节点。

## Risks / Trade-offs

- 图片节点消费方较多，如果遗漏某条读取 `result.primary` 的路径，主图切换会表现不一致
  - Mitigation: 抽取统一 helper，并在提示词引用、节点预览、执行输入三处统一接入
- 本地 FFmpeg 对远程 URL 或 data URL 处理不稳定
  - Mitigation: 切图前先把源图持久化到工作区素材目录，再交给 FFmpeg
- 多图平铺动画如果写得过重，可能影响画布性能
  - Mitigation: 只做轻量 transform / opacity 过渡，不引入复杂动画库

## Migration Plan

1. 兼容读取旧图片节点的单个 `source`
2. 新保存的图片节点以集合结构持久化
3. 运行时若没有集合字段，则自动退化为单图节点行为

## Open Questions

- 本轮默认不支持节点内图片拖拽排序，暂时按加入顺序展示
- 高清化先采用 FFmpeg 放大与锐化，不接入额外 AI 超分服务
